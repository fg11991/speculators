## 一、DSpark 离线训练时,显存到底花在哪

逐行读了 `src/speculators/models/dflash/core.py::_backbone_forward`、`dspark/core.py::forward`、`dflash/metrics.py::compute_metrics`。单个训练 rank、一个 step(记 `A=max_anchors=512`、`B=block_size=8`、`S=seq=2048`、`H=hidden=5120`、`V=vocab=151936`、`L=draft层=5`):

| 张量 | 形状 | 留到 backward | 你当前值下的量级(bf16/fp32) |
|---|---|---|---|
| **draft logits** `lm_head(hidden)` | `[1, A·B, V]` | **是** + 它的 grad 同样大 | 每份 `4096·151936·2B ≈ 1.24 GB` |
| **verifier targets** | `[1, A·B, V]` | 是(no_grad) | 1.24 GB |
| **verifier_logits 瞬态** | `[1, S, V]` | 否 | `2048·151936·2B ≈ 0.62 GB`(在整条 S 上算再 gather,浪费) |
| **TV loss fp32 中间量** | 多份 `[A·B, V]` fp32 | 瞬态,**峰值最凶** | 每份 `4096·151936·4B ≈ 2.49 GB`,同时活 3~4 份 ≈ **8–10 GB** |
| draft 层激活 | `~L×[1, A·B, H]` | 是 | 无 activation checkpoint,全留 |
| 输入 hidden_states | `[1, S, len(aux)·H]` | 是 | seq 短,`2048·3·5120·2B ≈ 63 MB`,小 |
| embed_tokens(冻结、**不被裁剪**) | `[V, H]` | 参数 | `151936·5120·2B ≈ 1.55 GB`,FSDP 会分摊 |
| lm_head / verifier_lm_head(**被 t2d 裁剪**) | `[V, H]` | 参数 | 各 1.55 GB(裁剪后 ÷4.7),FSDP 分摊 |

**主导项全是"词表宽" `V` 的张量,合计 ~12–15GB**,这就是 `anchor=512` 的天花板。draft 那 5 层的参数/激活是零头。

> 推论:**缩小 `V` 或 `A·B` 的有效计算量,收益是数量级的;去动 draft 层数/hidden 收益极小。**

`embed_requires_grad` 默认 False → embed_tokens 冻结、无优化器态;但它 **1.55GB 且不被词表裁剪**(输入 token 是全词表),是 FSDP 分摊的主要参数。`lm_head`/`verifier_lm_head` 走 `t2d` 裁剪(model.py:169)。

## 二、能立刻用的杠杆(按收益排序)

### 杠杆 1️⃣(头号):打开词表裁剪 `--draft-vocab-size 32000`

`load_verifier_weights` 用 `t2d` 把 `verifier_lm_head`/`lm_head` 都切到 `draft_vocab_size` 行,§一里所有 `[*, V]` 张量的 `V` 从 151936 → 32000,**主导显存 ~4.7×↓**(12–15GB → ~2.5–3GB)。EAGLE-3 经验 32K 基本不掉接受率([VocabTrim](https://arxiv.org/abs/2506.22694):裁 LM head 输出维最多省 75%、接受率几乎无损)。

```bash
    --draft-vocab-size 32000 \
```

✅ **你这条脚本零前置、开箱即用**:读 `scripts/train.py::parse_vocab_mappings` 确认——它优先找 `--data-path/{t2d,d2t}.npy`,没有就找 `--data-path/token_freq.pt` 自动建映射并缓存。而**你的 `prepare_data.py` 默认就把 `token_freq.pt` 写进 `--output`(=`OUTPUT_DIR`=`--data-path`)**(preprocessing.py:948,预处理阶段对 input_ids 数词频)。所以直接加 `--draft-vocab-size 32000` 即可,第一次跑会自动生成 `d2t.npy/t2d.npy` 缓存下来。

🔑 **hidden 缓存与 `draft_vocab_size` 完全解耦——开裁剪不用重生成 hidden。** 核过两侧代码:speculators 原生生成(`data_generation_offline.py`→`hs_{i}.safetensors`,只存 `token_ids`+`hidden_states`,offline.py:7)和 SpecForge 生成(`prepare_hidden_states.py`,DataPoint 只有 input_ids/loss_mask/hidden_state/aux/last_hidden)**都不落任何 vocab 宽张量、不碰 d2t/t2d**;词表裁剪纯粹是**训练时**对 `lm_head`/`verifier_lm_head` 切行(train.py `parse_vocab_mappings` + `load_verifier_weights`)。所以你可以在**同一份已生成的 hidden 上**直接扫 `draft_vocab_size × max_anchors` 组合,无需重跑生成。(`token_freq.pt` 只是"计数原料",不改 hidden、不改词表维度。)

> ⚠️ 一致性:开裁剪后 checkpoint 的输出词表是 32K,**部署端(vLLM/推理)也要用同一套 d2t/t2d 还原到全词表**。speculators 转换/部署会带 `d2t`,保持训练与部署映射一致即可。

### 杠杆 2️⃣:裁剪腾出空间后,直接抬 `--max-anchors` / `--total-seq-len`

`max_anchors` 与所有 `A·B` 张量线性相关。裁到 32K 后同样预算 `max_anchors` 约可 ×3~×4(512 → 1500~2000+),用二分法往上顶到快 OOM。`seq` 影响输入 hidden 和 verifier_logits 瞬态(你现在 seq 短、这俩很小),抬 seq 相对便宜。**建议先开 `--draft-vocab-size`,再顶 `--max-anchors`,最后视需要抬 `--total-seq-len`。**

### 杠杆 3️⃣:把全局 ZeRO-3 换成 HSDP —— 提速,不是省显存

你现在是 `--fsdp-shard`(无 `--fsdp-shard-size`)= **跨全部 64 rank 的 ZeRO-3**,每层参数 all-gather 都过跨节点 fabric,正是你脚本注释里 "29s→180s/it" 的那个坑。`apply_fully_sharded` 其实支持 HSDP(distributed.py):
```bash
    --fsdp-shard --fsdp-shard-size 8 \
```
**只在节点内 8 卡间切参数、跨节点复制**:参数 all-gather 只走节点内总线,只有每步一次的梯度 all-reduce 过跨节点 fabric。代价是每 rank 参数从 `/64` 变 `/8`(对 embed+两个 head 那点矩阵、64GB 卡上可忽略),换来跨节点流量数量级下降。**强烈建议在 32B 多节点上用这个替换裸 `--fsdp-shard`。**

> 📌 顺手把脚本头注释 "speculators has NO hybrid_shard/HSDP option" 改掉,已过时。
> 若词表裁剪后参数压力也降了,甚至可以试**纯 DDP(去掉 `--fsdp-shard`)**——那是你注释里最想要的最快路径,前提是 embed(1.55GB,不裁剪)+ 优化器在单卡放得下。

### 杠杆 4️⃣:already-on,别关 / 顺手修

- `--hidden-states-dtype bfloat16`(默认);dflash/dspark 默认全层 sliding window(window 2048),draft 注意力非平方,已是省的。
- 🔧 **`TARGET_LAYER_IDS="2 18 33"` 注释写的是 "Qwen3-8B 36 层",但你在跑 64 层的 32B**。`resolve_target_layer_ids` 对显式值不校验、原样用,这三层全挤在前半段,aux 覆盖不理想(**精度隐患,非显存**)。64 层建议按 low/mid/high 重选(如 `"3 31 59"` 一类),放量前值得改。

## 四、换更大模型(GLM-5.2 这类)还能用当前 8×8 910C 训 draft 吗?

架构量级(联网核过):

| 模型 | 总参/激活 | hidden | 层数 | vocab | 注意力 |
|---|---|---|---|---|---|
| Qwen3-32B(现在) | 32B 稠密 | 5120 | 64 | 151936 | GQA |
| GLM-4.5 | 355B MoE / 32B 激活 | 5120 | 92(3 dense+89 MoE) | 151552 | GQA |
| GLM-5 | 744B MoE / ~40B 激活 | ~6144(以 5.1 为参) | 78 | ~151k | **DSA 稀疏注意力** |
| GLM-5.2 | GLM-5 家族(1M 上下文) | ~6144 | ~78+ | ~151k | DSA |

### 4.1 训练 draft 这一步:能,而且比想象轻

**离线设计把"训 draft"和"验证模型多大"解耦**——训练时 NPU 里没有那 744B,只有:预生成的 `hidden_states`(磁盘按需 load)、`verifier_last_hidden_states`(H 宽)、`verifier_lm_head`(`[H,V]`,FSDP 分摊)。

你**当前就已经是 32B / hidden 5120**,GLM-5.x hidden ≈ 6144 只 **×1.2**;词表几乎不变。配 §二 词表裁剪 + 适中 max_anchors,单卡 64GB 宽裕。**MoE 对 draft 完全透明**:draft 永远是个小稠密 transformer,只吃验证模型吐的 hidden 向量。

### 4.2 真正变紧的两处(资源够,是工程适配量)

**(a) 用大模型跑推理生成 hidden —— 瓶颈在这。**
你现在生成走 `launch_vllm.py`(vLLM-ascend)。换 744B MoE 后:bf16 权重 ≈ 1.5TB,8×8=64卡×64GB=**4TB 聚合 HBM**,装权重+KV 有余量,**理论放得下**。但要:
- vLLM-ascend 支持 **GLM MoE 的专家并行 EP + TP/PP**;
- 支持 GLM-5 的 **DSA(DeepSeek 稀疏注意力)** 算子;
- **aux 层抓取 + verifier_last(pre-norm 末层)提取**要适配到 GLM 模型类(现在这套是 Qwen 系;换模型要重定位 hook/锚点)。
这些是"适配后能跑"的**"适配"主体**,不是资源不够。

**(b) hidden 磁盘/IO —— TB 级,必须提前压。**
每 token 存 `(len(aux)·H + H)·dtype`。GLM H=6144、抓 3 aux+1 last、bf16 → `4·6144·2B ≈ 49 KB/token`。你 `MAX_SAMPLES=300000 × seq 2048` ≈ 6e8 token → **~30 TB**。对策(都现成):`.ckpt.gz` 压缩(commit `2691887` 已支持)、少抓 aux 层、共享盘分片、边生成边训、必要时 hidden 存 fp8。

### 4.3 一句话回答

> **能。** 当前 8×8×910C(64GB)在**适配之后**足以训练 GLM-5.2 量级模型的 DSpark draft。约束点不在"训 draft 的显存"(离线解耦 + 词表裁剪后很宽松,你现在就已经是 32B),而是转移到 **① 起 744B MoE 分布式推理生成 hidden(EP/DSA/末层提取的适配)** 和 **② hidden 的 TB 级存储/IO(压缩+少抓层+流式)**。这两件是工程适配量,不是资源缺口。
